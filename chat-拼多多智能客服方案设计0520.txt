## 系统模块划分

不管多开方案怎么选，整体系统分为这几层：

- 每轮对话记录到本地数据库
- 定期由 LLM 批量处理，生成售前/售后问题分析表格

## 这对自动化流程的影响

- 模拟点击发送或按回车发送

## 两种视觉方案的选择

**方案A：传统 OCR + 模板匹配**
- OCR 用 PaddleOCR 或 Tesseract 提取文字和坐标
- 按钮/红点等用 OpenCV 模板匹配定位
- 优点：延迟低、成本低、离线运行
- 缺点：界面改版后需要重新调模板，维护成本高

**方案B：多模态 LLM 驱动视觉理解**
- 截屏直接发给多模态大模型（GPT-4o、Qwen-VL 等），让它理解界面状态并返回操作指令
- 优点：适应性强，界面小改不影响
- 缺点：每次截屏都要调 API，延迟高（2-5秒）、成本高、且对精确坐标定位不够可靠

**我的建议：方案A为主，方案B辅助**
- 日常的 Tab 切换、未读检测、输入发送走传统 OCR + 模板匹配，快且稳
- 图片消息理解、复杂界面状态判断走多模态 LLM
- 这样兼顾速度和智能

## 详细模块设计

### 一、视觉感知模块

**核心职责：** 把屏幕上的像素信息转化为结构化数据

**工作流程：**

1. 定时截屏（建议 1-2 秒一次，局部截取商家工作台窗口区域）
2. 对会话列表区域做 OCR，提取每个会话的：客户昵称、最新消息摘要、未读标记
3. 对 Tab 栏做 OCR/模板匹配，识别当前激活的店铺 Tab 和有未读消息的 Tab
4. 对当前打开的对话区域做 OCR，提取完整对话历史

**需要预先标定的区域（一次性配置）：**
- Tab 栏的屏幕坐标范围
- 会话列表的坐标范围
- 对话内容区域的坐标范围
- 输入框的坐标位置
- 发送按钮的坐标位置

因为分辨率固定，这些坐标可以写成配置文件，界面改版时更新即可。

---

### 二、调度模块

**核心逻辑：一个主循环**

```

    2. 切换到该 Tab
    3. 扫描会话列表，找到未读会话
    4. 点击进入该会话
    5. 提取对话内容（文字 OCR + 图片截取）
    6. 组装 prompt（对话内容 + 知识库 + 店铺信息）
    7. 调用 MiniMax M2.7 获取回复
    8. 执行输入和发送
    9. 记录到数据库
    10. 返回步骤3处理下一个未读会话
```

**优先级策略：**
- 等待时间长的客户优先
- 同一客户的连续消息合并处理（等客户说完再回复，避免打断）

---

### 三、LLM 调用设计

**Prompt 结构：**

```
[系统角色] 你是XX店铺的客服，风格亲切专业...
[知识库] 当前店铺的商品信息、退换货政策、常见话术（从markdown文件加载）
[对话历史] 最近N轮对话
[当前消息] 客户最新发送的内容（文字/图片）
[输出要求] 回复内容 + 问题分类标签
```

**图片消息处理：**
- 截取对话中的图片区域
- 作为图片输入传给 M2.7
- Prompt 中说明"客户发送了一张图片，请结合图片内容回复"

**知识库注入方式：**
- 20个店铺各自维护一份 markdown 知识库
- 根据当前 Tab 对应的店铺，加载对应知识库
- 如果知识库较大，可以做简单的关键词匹配，只注入相关段落，控制 token 消耗

---

### 四、数据记录与分析模块

**实时记录：**
- 每次对话交互存入 SQLite：时间戳、店铺、客户ID、客户消息、AI回复、问题分类标签

**定期分析：**
- 每天定时（比如23:00后）将当天对话批量发给 LLM
- 输出结构化的售前/售后问题表格
- 导出为 Excel，字段包括：问题类型、频次、典型案例、建议改进措施

## 补充设计细节

### 转人工机制

**触发条件：**
- LLM 判断客户意图涉及退款（关键词 + 语义双重判断）
- 客户明确说"转人工"、"找人工客服"等

**执行动作：**
- 自动回复一句兜底话术："亲，已为您转接人工客服，请稍等~"
- 该会话标记为"待人工处理"，后续消息不再自动回复
- 通过通知渠道告警（微信/钉钉/短信推送给你）

**你需要确认：** 告警通知走什么渠道？微信机器人、钉钉、还是其他？

---

### 上下文管理

**存储结构：**
- 以"店铺 + 客户昵称"作为会话唯一标识
- SQLite 中按这个标识存储对话记录
- 每次组装 prompt 时，查询该标识下最近 3 天的历史对话

**新会话判断：**
- 同一客户 3 天内再来消息 → 延续旧会话，带入历史上下文
- 超过 3 天 → 视为新会话，不带历史

**上下文裁剪：**
- 3 天内对话可能很长，需要控制 token 量
- 策略：保留最近 20 轮对话，更早的做摘要压缩（LLM 生成一段总结替代原文）

---

### 监控与运维

既然用专用机器 + 远程桌面，系统本身需要一些自我监控能力：

**健康检查：**
- 定时检测商家工作台进程是否存活，崩溃则自动重启
- 检测网络连通性（LLM API 是否可达）
- 检测截屏内容是否正常（防止窗口被遮挡或最小化）

**日志与统计：**
- 本地日志文件记录每次操作（方便排查问题）
- 每日统计：处理会话数、平均响应时间、转人工次数、LLM 调用次数和费用

**异常兜底：**
- LLM 连续超时 → 发预设话术"亲，稍等一下哦~"
- OCR 连续识别失败 → 暂停操作，发告警通知
- 程序崩溃 → 设置 Windows 计划任务自动重启

## 费用预估

**Token 换算：**
- 中文大约 1 个字 ≈ 1.5-2 个 token
- 输入 200 字 ≈ 300-400 token
- 输出 200 字 ≈ 300-400 token

但这只是单轮消息本身。实际每次调用还要带上：
- 系统 prompt + 知识库片段：约 1000-2000 token
- 历史对话上下文（最近几轮）：约 500-1500 token

**单次调用估算：**
- 输入 token：约 2000-3500（系统prompt + 知识库 + 历史 + 当前消息）
- 输出 token：约 300-400

**MiniMax M2.7 定价（当前公开价格）：**
- 输入：约 ¥0.001 / 千 token
- 输出：约 ¥0.004 / 千 token

（注意：MiniMax 的定价可能有调整，建议以官网最新为准）

**日均费用估算：**

| 项目 | 计算 |
|------|------|
| 日均对话次数 | 2500 次（取中间值） |
| 每次输入 token | ~3000 |
| 每次输出 token | ~400 |
| 日输入总量 | 750 万 token |
| 日输出总量 | 100 万 token |
| 输入费用 | 7500 × ¥0.001 = ¥7.5 |
| 输出费用 | 1000 × ¥0.004 = ¥4.0 |
| **日均合计** | **约 ¥11-12** |
| **月均合计** | **约 ¥330-360** |

**额外成本：**
- 图片消息调用（多模态）可能单价更高，但占比不大
- 每日批处理问题分析，额外增加少量费用
- 总体月成本预估在 **¥400-500** 左右

这个成本相对于一个人工客服的工资来说非常低。

## 分阶段开发计划

既然用 vibe coding 方式，建议按以下阶段推进：

### Phase 1：最小可用链路（单店铺单会话）

**目标：** 手动指定一个已打开的对话窗口，能自动读取最新消息、调 LLM、输入回复并发送

**拆解：**
1. 截取对话区域 → PaddleOCR 提取文字 → 验证识别准确率
2. 定位输入框 → pyautogui 点击输入框 → 输入文字 → 点击发送
3. 接入 MiniMax M2.7 API → 传入消息 → 获取回复
4. 串联 1-2-3，形成完整单次交互

**验收标准：** 客户发一条消息，系统能在 5 秒内自动回复

---

### Phase 2：单 Tab 多会话轮询

**目标：** 在一个店铺 Tab 内，自动检测未读消息，逐个处理

**拆解：**
1. 识别会话列表中的未读标记（红点/数字）
2. 自动点击未读会话进入对话
3. 处理完后切换下一个未读会话
4. 加入上下文管理（SQLite 存储，按客户昵称关联）

---

### Phase 3：多 Tab 轮询

**目标：** 跨店铺 Tab 自动切换，覆盖全部 20 个店铺

**拆解：**
1. 识别 Tab 栏的未读标记
2. 自动切换 Tab
3. 加载对应店铺的知识库
4. 优先级调度逻辑

---

### Phase 4：完善与加固

**目标：** 生产可用

**拆解：**
1. 转人工机制 + 告警通知
2. 异常检测与自动恢复
3. 数据分析模块（每日报表）
4. 图片消息处理优化
5. 操作节奏随机化（防风控）
